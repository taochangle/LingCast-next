# Companion host LLM compatibility — 2026-11-25

The observed host degradation exposed two LLM response compatibility issues:

- Default Qwen output included thinking markers in the content, took about 58.12 seconds for a topic probe, and was not a JSON-only response. Application operations have a 20-second deadline. An explicit optional `LLM_DISABLE_THINKING=true` setting sends `chat_template_kwargs.enable_thinking=false`. It is enabled only in this vLLM deployment; the template default is false so other compatible APIs receive no vendor extension. A comparison completed in about 6.46 seconds with twelve JSON topics and no thinking markers; the full-persona probe completed in about 10.24 seconds.
- vLLM normal responses contain `tool_calls: []`. The parser incorrectly treated any non-null field as a tool operation. It now accepts absent/null/empty arrays and still rejects nonempty arrays, malformed types and actual function calls. No tool execution was added, and the independent speech/content audit remains enabled.

Regression tests reproduce the empty-array rejection before the fix and verify both optional thinking behavior and rejection of actual tool calls. Go race tests and Compose configuration checks passed. Both changes were deployed and pushed.

After deployment, the live host generated and stored twelve topics successfully. The operator then restarted the separate LLM service while changing its configuration; it was still loading at the last check. Automatic spoken task completion after that restart remains to be verified. Topic generation alone is not evidence of successful automatic speech playback.
