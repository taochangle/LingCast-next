# Task 5 deployment and integration evidence

## Scope and choices

- Business Compose builds the TypeScript/React bundle and pure-Go server in separate stages, then serves both in Alpine with CA certificates, FFmpeg, FFprobe and tzdata. Named app-data preserves SQLite and uploaded files.
- The standalone AI Compose file has no app service or dependency. A Python 3.12 Worker and SRS talk over an internal streaming network. SRS has no host port. Worker uses its default network for signed business media and model requests. Optional models use the models profile. The topology needs one business HTTP(S) origin accessible to both Worker and browser. README documents a trusted HTTPS gateway or controlled private interface for real use, and the test-only Docker DNS alias is scoped to the CPU smoke.
- Required secrets fail Compose interpolation if blank. Published ports bind to loopback by default. .dockerignore allow-lists source build inputs and excludes environment files, local build outputs, weights, data, Git metadata, and .superpowers records. .env.example contains placeholders only.
- CosyVoice runs Python 3.10 / CUDA 12.1.1 cuDNN 8, Torch 2.3.1+cu121, pinned vendor requirements, upstream source 074ca6dc9e80a2f424f1f74b48bdd7d3fea531cc and pinned Matcha gitlink dd9105b34bf2be2230f4aa1e4769fb586a3c824e. Verified source/gitlink and Docker registry digest against the actual sources. DeepSpeed and PyWorld build with preinstalled torch and numpy, while the TensorRT package stub uses its own build dependencies.
- MuseTalk runs Python 3.10 / CUDA 11.8.0 cuDNN 8, Torch 2.0.1+cu118, and source 0a89dec45a0192b824e3cf4daf96c239440c5ed8. Verified the OpenMMLab CUDA 11.8/Torch 2.0 wheel index has the exact mmcv 2.0.1 CPython 3.10 Linux x86_64 wheel. Model downloaded weights and reference audio bind-mount separately. The MuseTalk cache and prepared assets persist. Deployment Compose uses real model service code and pre-acquired weights.
- SRS deployment uses Docker registry index sha256:5ed957dbebc48da42e928cebbc9446bced1c5afc58f816e122ce36d370af0113, verified to include arm64 and amd64. SRS config syntax passed in the exact image with no external network.

## Integration findings

- Worker preview previously called response.read(65536), so a slow FLV stream could fail to deliver a small first packet until much more data arrived. Focused local HTTP test sent only three bytes and held the connection open. RED timed out at response.read(3) after 2.0 seconds. GREEN after response.read1(65536) received the same bytes with upstream still open in 0.51 seconds. Backend controller flush was implemented separately by backend owner in f4fbf8b. The combined smoke validates the two proxies together.
- Reported the mismatch between business request text length and the 240-character resident renderer limit. Worker owner implemented segmentation. The Compose fixture rejects requests over 240 characters, verifies short manual/welcome text verbatim and verifies a longer Chinese manual input can be reconstructed exactly from renderer requests.
- The combined smoke walks real Go and Worker HTTP, upload and signed download, duplicate start conflict, Worker and Go preview authorization, SRS FLV header received over the browser query-token route, manual enqueue, platform mismatch, accepted/processed/retry ID acknowledgement and event dedup, exact long-text chunking, and end/stale token/stale task behavior. CPU fixtures return silence and solid-color JPEGs. No relay, platform, LLM or model network services contacted during smoke.

- Docker Desktop engine linux/aarch64, Docker Compose v5.6.1. `./scripts/check-compose.sh` passed five deployment configurations (business only; AI only with and without model profile; combined with and without model profile). `bash -n scripts/*.sh`, `python3 -m compileall -q worker services tests/integration` and `git diff --check` passed.

- Separate AI-only Compose used only Worker, SRS and a synthetic model fixture from the smoke overlay. It returned HTTP 200 with ready:true for an authenticated Worker health request, and 401 for an unauthenticated request. The service list had no app or GPU model container.
- `./scripts/smoke-compose.sh` passed with built app and Worker and SRS, including browser preview and collector acknowledgement. The final run on Worker revision 164143b and backend acknowledgement/flush revision f4fbf8b passed. Cleanup removed the disposable project, networks, volumes and app/Worker image tags.

## Review fix round 1

Whisper 20231117 builds from its source distribution. Its setup script imports `pkg_resources`, which a current isolated setuptools build environment no longer provides. The TTS Dockerfile now preinstalls that exact Whisper version with `--no-build-isolation --no-deps`. The existing setuptools 75.8.2, wheel 0.45.1 and packaging 24.2 supply its build tools. The normal full-requirements install resolves runtime dependencies and retains build isolation for TensorRT. [Whisper source](https://github.com/openai/whisper/blob/v20231117/setup.py) · [setuptools v82 history](https://setuptools.pypa.io/en/stable/history.html#v82-0-0)

- In a fresh CPython 3.10.21 environment with the three build-tool pins, default isolated `pip wheel --no-cache-dir --no-deps openai-whisper==20231117` failed with `ModuleNotFoundError: No module named 'pkg_resources'`. The exact new Dockerfile command returned `Successfully installed openai-whisper-20231117`. `pip show` confirmed version 20231117.
- `./scripts/check-compose.sh` passed all five deployment configurations and `git diff --check` passed. This check covers the Whisper package build and install. Full CUDA image build and GPU inference remain target-environment checks.
- The scoped `docker run --platform linux/amd64 --rm python:3.10-slim-bookworm` check reproduced the same isolated-build error. With the three tool pins, `pip wheel --no-deps --no-build-isolation openai-whisper==20231117` successfully built `openai_whisper-20231117-py3-none-any.whl`. Its metadata confirmed version 20231117 and the Linux x86_64 dependency `triton<3,>=2.0.0`.
