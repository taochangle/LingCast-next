# 数字人直播独立新版设计（待用户批准）

## 意图与范围

独立建设新版，复用 LingCast 已有配音、对口型、流式播放与插件链路；不改动或部署旧版。允许维护多个数字人，整个系统同时仅运行一场直播。面向标准 Docker Compose 部署，不制作 setup，不管理用户的 Docker。

## 已确认的产品行为

- 数字人拥有独立名称、人设和话术；每个数字人拥有多个形象，每个形象包含用户上传的形象图和多个 idle 视频。
- 素材提前制作，系统不生成形象图或 idle。开播必须选择数字人、其所属形象及平台（抖音或小红书）。本场固定形象，换形象必须结束后重新开播。
- 继续使用用户主动启动的 Chrome 插件采集。两平台各自适配 DOM，转换成统一事件；页面没有的信息不猜测。不得操作平台评论输入框。
- 话术包含无人互动时的主持，以及欢迎、感谢、评论相关表达。固定话术原文口播；AI 自由回复受人设约束。这是基于用户对“两者都包含”的确认形成的解释，须随本文确认。
- 每次 AI 回复注入业务服务器当前日期、星期、时间和明确时区。时间来源不采用观众或插件提供的值。
- 业务服务与管理端采用 Go 后端及 Web 管理界面；保留精简 Python Worker，处理流式音视频、播放与 FFmpeg 衔接。Python 配音和对口型独立服务。

## 方案比较与选择

1. 原仓库内重构：复用方便，但与旧客户端、指定人物换装及历史配置耦合。
2. 独立新版复用成熟链路：重新组织数据和业务边界，移植并验证必要链路，隔离旧版。用户已选择此方案。
3. 连 Worker 全部重写 Go：减少 Python 范围，但实时链路重写风险较高。用户选择第一版保留精简 Python Worker。

部署选择标准 Compose，放弃原生 Windows Python 引擎包和 setup。Windows 使用 WSL2 的 Linux 容器；Linux Server 使用 Docker 与 NVIDIA 容器支持。两平台镜像分别验收，不能以容器可启动代替真实 GPU 验证。

## 系统边界

- Go 主服务：人物、形象、素材、话术、单场直播状态、事件鉴权去重、互动调度、LLM 调用和服务端时间。
- 管理界面：上述数据维护、开停播、手动口播、主持控制、配置及连接检查、播放预览和错误状态。
- Python Worker：消费带场次身份的任务，调用配音与对口型服务，维持 idle 与说话画面切换，驱动 FFmpeg。移除换装、唱歌和旧客户端专属逻辑。
- 配音服务、对口型服务：以现有 CosyVoice/MuseTalk 链路为复用起点，固定依赖与模型版本。通过独立适配协议服务 Worker，不要求任意第三方地址直接兼容。
- Chrome 插件：抖音、小红书适配器与统一上报协议。旧小红书代码需重新核对，抖音适配不能视为已实现。

## Compose 交付

- `compose.yaml`：Go 主服务、管理界面及实际所需业务依赖。
- `compose.ai.yaml`：Worker、配音、对口型，以及流媒体输出所需组件。Worker 的加入是本轮已确认的范围修正。
- 本地 GPU：组合两份配置，在同一部署内连通。
- 本地无 GPU：本地运行业务配置，远端 GPU 服务器运行 AI 配置；业务通过配置连接 Worker，Worker 在远端调用两个模型服务。
- 配音、对口型地址均可配置；选用远端服务时不启动对应本地模型容器。模型侧接口可以发布端口供授权客户端调用。默认仅发布必需端口，远端通信配置认证，支持经 HTTPS 网关访问。
- 数据、素材、模型和预处理缓存使用持久化卷；更新镜像不得清空。系统宿主机负责驱动，镜像固定用户态运行库；不在 WSL 内安装 Linux 显卡驱动。

## 数据和运行约束

数字人、形象、idle、话术、直播场次为独立实体。形象属于一个数字人，idle 属于一个形象；拒绝跨人物绑定。场次记录选定人物、形象、平台和状态。

开播原子占用系统唯一直播槽位，重复或并发开播返回冲突。启动前校验素材及 Worker/模型就绪；启动失败释放槽位并保留错误。结束时停止本场输出并使其任务和采集凭据失效；旧场次事件不得进入新场次。服务重启后不能把遗留状态误认为仍在直播，应核对 Worker 状态，无法核对时标记故障并允许显式停止清理。

按场次鉴权采集事件，校验所选平台，按事件身份去重。事件队列有界且有过期规则，具体数值由实施计划依据现有链路选定并记录，不无限积压。

## 播放与互动（以下为设计建议，随本文审批）

- 同一形象 idle 自动顺序轮播；说话使用该形象指定默认 idle 作为口型底片，第一版不按情绪挑选视频。素材需验证完整解码、画幅、帧率、无声 idle 及人物外观由人工确认。
- 开播前完成指定底片的人脸预处理和模型就绪检查。缓存按模型、音色、文字和底片指纹隔离。
- 现有短段边界调度原则沿用：手动口播 → 礼物感谢 → 点赞感谢 → 评论回复 → 欢迎 → 自动主持。当前短段讲完再取下一项，停止直播可取消任务。
- 主持固定稿按序循环，可暂停；欢迎和感谢支持固定模板，评论默认使用 LLM，管理员可选择固定稿或手动口播。空话术库保持 idle，不凭空自动编稿。
- 数字人配置音色；LLM 采用可配置的 OpenAI 兼容接口，不在本项目内安装 LLM。
- 全局直播时区默认 `Asia/Shanghai`，可配置。注入业务服务器时间；模型机器的默认时区不影响互动。时间相关自由回复不长期缓存；固定稿不自动改写，运营者负责不上传过时稿。
- 沿用现有 Worker → FFmpeg → SRS 链路：SRS 提供后台预览所需流，独立 FFmpeg relay 从 SRS 拉流并按管理员配置的 RTMP/RTMPS 地址和密钥转推平台。不依赖 OBS，不自动登录平台；外部转推必须由管理员显式启用，选择平台本身不触发转推。

## 验收与限制

验收覆盖人物和素材归属、并发开播互斥、固定形象、两平台事件隔离、旧场次拒收、话术原文播放、人设和时间注入、模型失败与停止清理、卷持久化。

分别验证本地完整 Compose、业务本地/AI 远程两种拓扑，并在 Windows WSL2 NVIDIA 与 Linux NVIDIA 环境实际生成和播放。CPU mock 测试不等于 GPU、真实平台 DOM 或长时间直播验收。最低驱动、显卡架构、显存、系统版本及模型分发许可必须在发布前核定，不预先承诺全型号兼容。
